执行结论

Tekon 已形成测试较强、边界说明诚实、治理意识较好的本地交付框架，但当前主路径仍是“一次性启动完整 workflow 并观察结果”。它还不是一个人类可以自然进入、持续追问、随时纠偏、逐步升级到受控交付的研发工作台。

产品合同错位界面叫 Session，实际是一次性 run 观察器；没有 follow-up、steer、durable inbox 或真实 provider streaming。
复杂度收益不对称已经承担 Session/Event/Job、Profile、Automation、Goal、DSH bridge、兼容驱动与双写投影成本，却没有权威 Session log。
运行权威不成立Web 与 CLI 都能启动 JobRunner，共享 SQLite/Git 工作区，缺少 single owner 或覆盖全部副作用的持久 fencing。
入口可立即改善本 PR 已让无参数运行显示成功帮助、把人类路径前置，并统一 CLI 与 updater 的根产品版本。

P0：必须解决

  1. Session 产品合同不成立：默认启动完整 standard-delivery，Composer 不能在当前会话继续输入，事件在执行完成后合成。
  2. Runtime 没有单一执行所有者：Web 与每个 CLI 进程都可能领取同一仓库的工作；数据库 claim 不能约束 Git、文件、artifact 和子进程副作用。
  3. Shutdown 不是 quiescent shutdown：最多等待约 5 秒后清理进程内状态，没有证明执行器、子进程和写入均已停止。
  4. 事实源分裂：session_events 是旧领域写入后的 best-effort projection，不是可重建模型上下文和业务状态的权威 log。

P1：重要问题

  • DSH bridge 仍固定 0.1.1-rc.2 的 headless one-shot 边界，而官方已经有 SDK/JSON-RPC 与 ACP profiles。
  • Profile、Automation、Goal、兼容 Driver、双写和双 composition root 先于真实消息流、第二次输入、持久 inbox 与恢复，过度实现顺序反了。
  • 默认完整交付缺少启动前的模式、角色、gate、网络、成本和副作用预览。
  • Session 列表应按最近活动和需要用户行动排序，而不是主要按创建时间。
  • TopBar 长期暴露 token 字符串，长 Session 也没有分页、虚拟化、摘要和上下文压力合同。
  • 产品信息架构仍中英混杂，并直接暴露 Session/Event/Job/Profile/Gate 等技术名词。
  • 合并 gate 与产品验收 gate 没有分离；CI 全绿不能自动关闭递延的 P0。

本 PR 已修复

无参数成为入口tekon 与 tekon help 输出一致，返回码为 0，不再把首次探索当成错误。
帮助页人类优先先给出 tekon ui、tekon run "你的需求" 和命令帮助，再展示完整高级命令。

测试与版本单测锁定新行为；实际行为改进按仓库规则提升到 0.16.0。

推荐顺序

  1. 运行权威：single-owner daemon、CLI/Web 客户端化、quiescent shutdown。
  2. Collaborate vertical slice：真实 streaming、durable inbox、follow-up、steer、cancel、resume 和重启恢复。
  3. 显式升级到 Deliver：先确认需求卡与 run plan，再进入现有 role/gate/artifact/PR 治理。
  4. 最后恢复横向平台化：只有纵向闭环通过后，才扩 Profile、Automation、Goal、多 workspace 和 subagent。
