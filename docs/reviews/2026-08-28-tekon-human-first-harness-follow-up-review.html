产品逻辑与 UI/UX

公开的“受控交付”合同已经诚实

首页标题、CTA 和 Composer 都明确说明会启动完整 standard-delivery 链路，并提示轻量协作、追问和转向尚未开放。因此当前问题不是“文案假装已有聊天产品”，而是受控交付工具还不足以成为普通人的日常研发工作台。

持续人类交互仍是产品 P0

  • 详情页没有当前 Session 输入 Composer；
  • followUp、steer、resume 仍不可用；
  • 事件主要在 one-shot provider 结束后摘要化；
  • blocked workflow 只能恢复或诊断，不能补充输入后继续同一 Turn。

列表不是实时行动队列

SessionsPage 只有一次查询和手动刷新。详情页的 session stream 可以 invalidate list cache，但用户停留在列表页时没有 workspace stream。建议后续增加 lightweight workspace revision/stream，而不是给当前会闪 loading 的 query hook 粗暴加轮询。

视觉证据边界

Runtime 与事实源 P0

没有单一执行所有者

Web 与 CLI 都能启动 JobRunner，共享 SQLite、Git worktree、运行目录和子进程。job owner/status 条件写与 Git CAS 有价值，但没有覆盖 Node、Artifact、Audit、Gate、Delivery、文件写入和 subprocess 的统一持久权威。迁移里已有 run_locks 表，却没有生产 Runtime 协议使用它，容易产生错误安全感。

Shutdown 非 quiescent

stop() 最多等待约 5 秒便清理进程内引用；它没有证明 executor、子进程、Git/文件写入和 listener 已经 join。正确顺序应是停止领任务、持久取消/暂停、abort+kill、join 副作用、确认无 late writes，最后释放 owner 和关闭 DB。

Session 事实源仍分裂

旧领域表是事实源，session_events 是 best-effort projection。这对 observability 过渡合理，但不能承担模型历史、durable inbox、fork/resume 和 crash recovery 的权威事实链。本轮活动排序需要同时参考 event 与 session row，正好证明该边界尚未收敛。

推荐：优先 single-owner daemon；Web、CLI 和 IDE 统一做客户端。第二 owner fail-fast，并显示 owner PID、启动时间、socket 和恢复操作。

DeepSeek Harness 对齐

当前 dsh-headless 是 goal-only、one-shot provider bridge，不是 Tekon Runtime 已经“基于 DSH”。Tekon 仍自持 Session、Job、Workflow、Gate、persistence 和 UI。

官方现有 sdk JSON-RPC profile 与 acp persistent-agent profile，后者支持 session new/list/resume、语义更新、取消和标准协议控制。下一步应先做边界 ADR：DSH 是 provider、持续 Session Runtime，还是仅作为架构参考。不要同时扩展 Tekon 自己的完整 AgentDriver，又继续加深 headless ACL。

  • Architecture
  • Agent lifecycle
  • Session persistence
  • SDK profile
  • ACP profile

Harness 官方 Safety 仍明确说明其未经过安全审计，sandbox、approval 与 permission 不保证隔离。Tekon 不能把安全责任外包给 DSH。

过度实现与代码风险

表面当前事实判断
