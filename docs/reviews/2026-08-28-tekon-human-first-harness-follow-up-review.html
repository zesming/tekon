P0：稳定产品仍不能通过的原因

1. Runtime 没有单一执行权威

Web 与 CLI 都能启动 JobRunner，并共享 SQLite、Git refs、worktree、运行目录与子进程。Job owner 条件写和 Git CAS 只覆盖局部，无法贯穿 Node、Artifact、Gate、Audit、Delivery、文件和进程副作用。

2. Shutdown 不是 quiescent shutdown

job-runner.stop() 在固定等待后清理进程内状态，无法证明 provider、子进程、Git/文件写入和异步 listener 已全部停止。

3. Session Event 仍是 best-effort projection

旧领域表先成功，Session Event 追加失败不影响主路径。这对观察面合理，但不能承担模型历史、durable inbox、follow-up/steer、fork、resume 与完整 replay。

4. 持续协作轨道尚不存在

当前 Deliver 路径文案诚实，但 Composer 只能创建新 run；followUp、steer、resume 仍未生产实现，Provider 事件也不是执行期真实流。

P1：产品与实现问题

  • 列表非全局实时：只在 Session detail 的 SSE 事件到达时 invalidate 列表，停留在列表页仍依赖刷新。
  • 相对时间静止：“刚刚 / N 分钟前”不会随时间自行推进。
  • Deliver 缺少启动前预览：角色、Gate、Provider、网络、超时、成本影响因素和审批点不可见。
  • Token 暴露实现细节：应最终收敛为连接状态和显式重新授权。
  • 列表查询随历史增长：当前 LEFT JOIN + max(timestamp) + group by 每次聚合事件历史。
  • 长 Session 无有界合同：分页、虚拟化、摘要、turn 导航和上下文压力仍缺失。
  • 术语偏工程内部：Session/Event/Job/Profile/Gate 应退出普通用户主路径。
  • DSH bridge 仍是旧 one-shot 边界：固定 0.1.1-rc.2，尚未重新评估 SDK/ACP。

DeepSeek Harness 对齐

官方架构把 Session log 作为模型上下文、replay、fork、resume 和 transcript 的来源，并把 durable Session events 与 live Agent events 分离。当前 profiles 包括 web、headless、sdk、sdk-minimal、acp；最新 prerelease 继续增强运行中消息排队、回合导航、token 用量和 ACP 会话控制。

问题不是局部代码写得差，而是系统级抽象顺序领先于用户纵向闭环。

推荐实施顺序

  1. Runtime authority：single-owner daemon、客户端化、quiescent shutdown。
  2. Collaborate vertical slice：真实 streaming、durable inbox、follow-up/steer/cancel/resume、重启恢复。
  3. Collaborate → Deliver：显式升级、run plan、复用现有治理链。
  4. Scale and polish：summary projection、分页、虚拟化、未读和全局实时任务列表。
