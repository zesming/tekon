第 26 轮整改执行方案：取消恢复、退出证据与安全重启

2026-09-05 · PR #11 · 基线 8141c4b69fb59988ff7c7e6266f3d5639c386131 · 计划版本 0.24.0

本轮完成取消控制与观察恢复、租约失效后的安全处置、可重试的用户入口和真实生命周期验收。原 R26-01/02 已修复，不重做受理、RunPlan 或 Provider 架构。本文是经独立设计评审放行的执行合同；实施结果见整改验收记录，计划本身不作为运行通过的证据。

1. 证据与决策

  • 原第 26 轮报告及追加批注 §10 是问题依据。基线两份 R26 回归共 12 项本地通过。
  • 独立 reviewer 以真实源码和 SQLite 复现：TTL 内快速重启错过唯一一次 stale 扫描；重复取消无法修复 Session active。Web cancelled 状态隐藏取消入口、Flash 无 Live Region 均有源码依据。
  • 独立 reviewer 在 Linux 使用与 Gateway 相同的 detached:true 真实 spawn：owner 被 SIGKILL 后，子进程仍为非僵尸存活状态，PPID=1。已清理诊断进程组。该实验不是完整 Provider 验收，但足以否定“租约过期即物理退出”。
  • 不采纳新增 cancel marker 表的建议：旧测试锁定的“重复取消不更新 Session”是本次要修的行为，不是额外权限边界；Session 已绑定原 Run，显式取消可修复它的观察。不用新表复制权威状态，也不用事件缺失推导物理停止。
  • 不采纳“每轮重排过期 Job 后自动执行”的候选补丁：未完成 Agent 有部分保护，但在飞 Gate 尚未记录结果时会自动重跑，可能与孤儿进程并发。先前代理提前写入的候选已隔离到本轮临时目录，生产源码和测试恢复基线。

2. 产品与交互合同

2.1 取消与重试

首次取消保留 3 秒二次确认。反馈分别表达原 Run 的终态、取消控制是否待投递，以及退出证据，不能把其中任一项称为全部后台进程停止。

Run cancelled 后，详情及 Session 侧栏根据服务端持久 Run/Job/Session 信息展示恢复说明和“重试取消”入口；刷新、重连或进入另一页面仍可操作同一个 runId。成功或失败都刷新相关观察查询，失败说明持续显示，不只保存在短暂 Flash 中。passed/failed 已先完成时不提供取消补发、不改终态。

读接口派生 cancelRecovery：是否需要重试控制、是否需要修复观察、当前 Job 标识与退出证据（confirmed / unconfirmed）。这里只陈述 Tekon 管理的执行句柄证据；无证据时显示未确认。读失败显示未知，不沿用“已停止”结论。字段进入现有受作用域约束的 Run/Session 映射，避免只在新 RPC 返回中存在而刷新后丢失。

2.2 租约失效与显式恢复

对已被认领、随后租约过期的 Job，后台有界巡检将其收敛为 interrupted，而非重新排队执行。只有 workflow-run/workflow-resume/goal-run 这三类执行 Job 才协调关联非终态 Run 为 interrupted，并让 Session 显示需要处理；automation 仅收敛自身，不改变 Run/Session。原取消赢家保持 cancelled。尚未认领的 queued Job 继续正常启动，健康 owner 的新租约不能被旧扫描覆盖。

正常关闭完成执行器排空且受管理句柄退出的 interrupted Job，记录本方案定义的新版退出证据，可沿既有显式恢复入口继续。旧 abortState=stopped 不作为退出证明；租约失效或硬关闭超时没有新版证据时，恢复前提示“旧进程退出未确认”，由用户确认已经检查并停止旧进程。

确认绑定 previousJobId，服务端同库事务重新检查当前 Run、最新 Job、终态和活跃 Job，再受理恢复，防止旧页面确认作用于新一代执行。Web 显示复选确认；CLI resume 增加可选 --confirm-stopped 和与之配套的旧 Job 身份，缺少确认时返回可操作错误与身份，不静默启动。审计只记录人工确认，不冒充 OS 探测证明。

2.3 通知与布局

Flash 使用常驻的非模态通知区域，消息插入前区域已挂载；错误与一般状态分别提供合适的 Live Region 语义，避免嵌套重复播报。关闭按钮中文命名，操作不无故转移焦点。取消恢复说明在详情持续存在。

对 320/390/768/1440px 核验实际取消文字、长错误、恢复确认及相关主要页面。现有 CSS 的普通取消文案未复现横溢，不能仅凭 max-width 数值修改布局；只有实际几何或交互失败才改样式。手册同步两步确认、真实终态、重试、退出未确认与恢复门槛。

3. 实现合同

3.1 同库幂等取消观察

在 SessionStore 增加窄范围的取消观察协调操作：BEGIN IMMEDIATE 内验证 Session 与 Run 绑定及 Run cancelled，补齐缺失的 agent/cancel-requested / agent/cancelled，更新 Session 状态，一次提交后只发布新事件。已有事件保持 seq/内容不变，并发进程重试不会双发；不能使用先 list 再逐次 append 的多事务实现。

SessionService 顺序保持终态 CAS → Job 控制投递 → 观察协调。Job 投递失败仍可返回错误，但持久 cancelled 意图供显式重试及后台补发；观察错误不得撤销已记录终态或前面的控制。无 Session 时不创建 Session/事件，仍取消 Run；passed/failed 冲突立即保持原赢家。

后台在现有串行轮询中协调 cancelled Run 尚存的活动执行 Job，并修复取消观察；复用同一个 store 操作和既有 requestCancel 协议，不另建后台服务或第二套事件语义。每轮最多处理 100 个候选，使用稳定主键游标分页，单项失败也推进游标；扫描到末尾后回绕，使失败项在后续轮次重试。单项异常隔离，stop 后不再开启下一页，不因首批持续失败而饿死后续 Run。

3.2 周期恢复与停止证据

在现有 poll 单一在途任务内安排受限的 stale 恢复和取消补发；stop() 进入 draining 后不再发起新扫描或新 claim，并等待同一轮在途工作结束。扫描和修改的 owner、状态、lease cutoff 条件在同一事务复核，健康续租和终态赢家优先。

已认领的过期 Job 使用现有 interrupted 状态与 abortState 区分退出未确认；不依赖裸 PID 存活判断，不按 owner 字符串猜测进程身份，不自动重跑 Gate/Agent/automation。取消中的过期 Job 保持取消语义但不伪写 stopped。关联 Run/Session 按当前权威状态收敛，禁止过期 executor 回写新一代执行。

正常 stop 的已排空分支记录新版退出证据；硬超时或无退出证据分支保留未确认。requestCancel 把 interrupted 视为终态，避免 owner=null 的递归重试。CLI 等待循环将 interrupted 视为终态并给出恢复说明，避免新恢复策略导致永久等待。

新增 Job 的 nullable exit_evidence 列，结构为 version=1、kind=never-started/managed-handles-closed、observedAt；证据属于该 Job，不是新取消状态表。历史 null/缺失一律 unknown，旧 stopped 不回填。新版 enqueue 与 admission 初始 Job 同事务写 never-started，claim 原子清空；取消时只保留已有的 never-started，不能从旧 queued 推导未执行。managed-handles-closed 仅在生产执行器 Promise 已排空、该 Job 执行 scope 内全部受管理句柄确实收到 close 后写入。Gateway 硬结算、kill 成功或 unregister 本身不构成证明；未 close 的句柄保留未确认记录，迟到 close 不能覆盖新一代执行。

Registry 按 Job 执行 scope 跟踪并映射现有 runId 调用，防旧代 close/kill 污染新代；Gateway/Registry 一起修改和测试。人工确认只写 Audit，不写物理退出证据。证据只覆盖 Tekon 管理的句柄，不扩称逃逸进程或所有系统后台活动。

实现补充（2026-09-06）：为关闭旧 executor 在下一次 poll 前回写的窗口，生产执行链在现有 WriteQueue 中携带 Job/owner 作用域，每次数据库写入均在同库事务复核所有权。事件订阅者处理独立的后台操作，不继承发布者的执行租约；定向测试覆盖延迟就绪度评估在原 Job 完成后仍可入队。生产 Gate 实进程取消测试还发现旧失败分支可将 cancelled 覆盖为 blocked，相关执行状态写入使用现有终态 CAS 保护。上述补充与代码、测试一起进入独立审阅，不视为本轮已最终放行。

3.3 恢复请求与查询

扩展现有恢复输入与输出合同，不新建命令或状态表。所有执行恢复入队入口共用同库事务守卫：确认、最新代次、Run 终态和活跃 Job 复核后才入队并记录人工确认 Audit。最新执行 Job 只含 workflow-run/workflow-resume/goal-run，按 createdAt 后 id 稳定排序；同库新入队时确保 createdAt 严格晚于该 Run 先前执行 Job，避免同毫秒随机 id 改变真实代次。readiness/delivery 等 automation 不参与恢复代次。

采用同快照 sessions.getRunRecovery(runId) 返回 cancelRecovery 与 resumeRecovery，后者含 previousJobId 和 requiresConfirmation。历史 interrupted 无执行 Job 时 requiresConfirmation=true、previousJobId=null；输入必须明确携带 null（不能等同省略），事务确认最新执行 Job 仍为空后受理。确认错代返回 stale-confirmation，未确认返回 exit-unconfirmed，不创建新执行。

Web gate.approve、CLI --approve-human 等审批后恢复入口同样使用守卫。可预先识别未确认退出时，在写审批决定前拒绝并返回恢复信息；若检查后发生竞争、审批已经记录但入队遭拒，准确返回“审批已记录，运行尚未恢复”及当前恢复信息，保留已记录审批，不说审批回滚或运行已启动。旧 cancelStaleActiveJobs 不得将未知退出写成 stopped 或绕过确认。

一次确认恢复应真正继续执行：事务取得恢复权后收敛上一代遗留 running Node/RoleRun 为 interrupted，保留 Worktree 与已完成 Agent 的证据；已完成 Agent、待执行 Gate 从 Gate 位置恢复，未完成 Agent 从允许恢复的节点状态继续。取消/并发恢复赢家优先，不能让用户第二次点恢复才通过 stale-running 检测。

Run 映射、Session 详情和 Web 控件使用同一派生规则；各读取入口保持现有认证及仓库 scope。退出证据不得由前端猜测、SSE 事件缺失或没有活动 Job 单独推导。
